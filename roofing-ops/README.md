# roofing-ops: a small Retool back end, built fresh

A sample internal tool for a roofing company, built to show how we structure Retool work:
queries, access control, a workflow and an AI agent that all share one set of rules.
Nothing here is client code. Sample data is generated (1,200 jobs, 3 regions, 6 crews).

## What's in it
| Folder | What it is |
|---|---|
| `sql/01_schema.sql` | Jobs, customers, crews, regions, insurance claims, inspections, audit log |
| `sql/02_access.sql` | **Who can see which rows**, enforced in Postgres: `api.jobs_list`, `api.claim_detail`, `api.pipeline_by_region`, `api.set_job_status` |
| `sql/04_workflow.sql` | Idempotent `api.record_inspection` for the webhook workflow |
| `queries/` | The Retool resource queries, exactly as they go into the query editor |
| `workflow/` | Retool Workflow `inspectionWebhook`: signature check, validation, idempotent insert, retry, error handler |
| `agent/server.py` | MCP server with 3 tools. The agent calls the same api.* functions, so it can't see more than the user |
| `tests/`, `agent/`, `workflow/*.test.js` | 37 tests against a real PostgreSQL 16 |

## Access model
- The Retool resource connects as `retool_app`. It has **EXECUTE on four functions and no table access**.
- Queries pass only `{{ current_user.email }}`. Role, region and crew come from `core.app_users`.
- Rules live in one SQL function, `api._can_see`, used by reads, writes, aggregates and the agent.

| Role | Rows | Phone | Contract $ | Claim / policy no. |
|---|---|---|---|---|
| admin | all | full | yes | yes |
| ops_manager | own region | full | yes | restricted |
| estimator | own region: own jobs + open leads | full | yes | restricted |
| crew_lead | own crew, scheduled to complete | masked | hidden | restricted |
| claims | insurance jobs only | masked | yes | yes |
| unknown / inactive | none | | | |

## Run the tests
    createdb roofing
    for f in 01_schema 02_access 03_seed 04_workflow; do psql -d roofing -f sql/$f.sql; done
    pytest -q tests agent           # 23 tests (Postgres + MCP agent)
    node workflow/blocks.test.js    # 14 tests (workflow blocks + idempotent SQL)

`sql/03_seed.sql` is generated by `python sql/03_seed.py`.

## What was hard
1. **The access rule broke the index.** With the rule only inside `api._can_see`, Postgres couldn't use an
   index, so at 480,000 jobs every page scanned and sorted every job (204 ms). We kept the rule as the single
   source of truth and added a per-role "scope" predicate (region, crew or insurance) with one index per
   scope in the list's sort order. Now 1.9 ms, and all tests pass unchanged.
2. **A type cast only the locked-down user exposed.** `::core.job_status` worked as the DB owner but failed
   as `retool_app`, which can't see schema `core`. Functions now take text and validate inside. Every test
   connects as the Retool user for this reason.
